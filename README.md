# 파워넷 ESG 데이터 입력플랫폼

3법인(서울 본사 · 중국 심양 · 베트남 빈푹)의 환경·사회 데이터를 한 곳에 모으는 입력플랫폼.
경영지원실이 AI를 활용해 **자체 구축**한다. 연 운영비 약 10만원.

목표는 2027년 지속가능경영보고서를 외주 없이 발간하는 것이고, 그 전에
고객사 탄소데이터 요구와 베트남 현지 법정 보고(2027-03-31)에 대응할 수 있는 상태를 만든다.

## 구조

```
wrangler.toml       배포 설정 (D1 · R2 바인딩)
db/schema.sql       테이블 15 · 트리거 7 · 뷰 3
db/seed.sql         기준정보 — 법인 3 · 역할 13 · 지표 49 · 담당배정 111
db/factors.sql      배출계수 — 계수 정책 + 3개 지역 전력 배출계수
db/verify.py        제약 검증 23항목
db/g3.py            산정 검산 84항목 — 손계산과 API 산출값 비교 (G3 게이트)
src/api.js          Worker — 라우팅 · 인증 · 기준정보 API
src/entry.js        입력값 처리 — 시트 조회 · 저장 · 증빙 업로드
src/review.js       현황 보드 · 검증·승인 · 2단 확정
src/calc.js         배출량·에너지 산정 · 연간 집계 · 비율지표 재계산
public/index.html   앱 셸
public/app.js       화면 로직 (라우팅 · 기준정보 · 시스템 상태)
public/input.js     입력 화면 (월간 시트 · 모바일 카드) + 3개 언어 사전
public/review.js    검토 화면 (현황 보드 · 검증·승인 · 연간 집계)
public/app.css      스타일
```

**의존성은 `wrangler` 하나다.** 프레임워크·번들러·빌드 단계를 쓰지 않는다.
파일을 고치고 `npm run deploy` 하면 끝이다.

이것은 기술적 취향이 아니라 성공 조건이다. 유지보수 주체가 1인이므로,
빌드 체인이 복잡해지는 순간 6개월 후 수정 불가 상태가 된다.

## 이 시스템에 개인정보가 없는 이유

인사·안전보건 데이터를 다루지만 **개인정보를 한 건도 보유하지 않는다.**
중국 PIPL과 베트남 개인정보보호법이 2026년 1월부터 국외이전 제재를 강화했고
(위반 시 매출의 최대 5%), 이 문제를 조심으로 피하지 않고 **설계로 피했다.**

| 단계 | 조치 |
|---|---|
| 저장 구조 | 이름·사번·이메일·연락처 **칸이 존재하지 않는다**. `db/verify.py`가 컬럼명을 전수 스캔해 확인 |
| 사용자 기록 | 사람이 아니라 **역할코드**를 기록한다 (`SY_OWNER`). 이메일 매핑은 `ROLE_MAP` 시크릿에만 있고 DB에 없다 |
| 증빙 첨부 | 인사·안전 지표는 **첨부 경로 자체가 없다**. DB 트리거가 거부하고, 기준정보 화면에서도 이 정책을 바꿀 수 없다 |
| 입력 형태 | **자유 텍스트칸이 없다.** 미확보 사유도 선택형 6개뿐이다 |

플랫폼에 올라가는 것은 *"심양법인 4월 인원 182명, 재해 1건, 총 근로시간 31,240시간"* 같은
집계값뿐이다. 개인을 식별할 수 없는 집계값은 개인정보가 아니므로 국외이전 규제의
적용 대상 자체가 되지 않는다.

## 산정값을 믿을 수 있는 이유 (G3 게이트)

화면은 틀리면 고치면 된다. **틀린 배출량을 고객사에 제출하면 되돌릴 수 없다.**
그래서 산정 로직은 "돌아간다"가 아니라 **"손계산과 일치한다"**까지 확인했다.

`npm run g3` 은 로컬 DB에서 **원본 입력값만** 읽어 파이썬으로 다시 계산하고,
API가 낸 값과 비교한다. 계산식을 `src/calc.js` 에서 옮겨오지 않고 정의대로 다시 썼다 —
같은 코드를 두 번 돌리면 같이 틀리기 때문이다. **현재 84항목 전부 일치.**

검산 예시

| 대상 | 손계산 | 산출값 |
|---|---|---|
| 심양 2026-09 Scope 2 | 126.5 万kWh × 10,000 × 0.0005306 | **671.209** tCO2 ✅ |
| 심양 2026-09 에너지 | 1,265,000 kWh × 0.0000036 TJ/kWh | **4.554** TJ ✅ |
| 심양 2026-09 TOE | 4.554 TJ × 1,000 ÷ 41.868 | **108.770** TOE ✅ |
| 본사 2026-09 Scope 2 | 19,100 kWh × **0.342 배분** × 0.0004173 | **2.7259** tCO2eq ✅ |

W3에서 잡은 것 — 전부 "돌아가지만 값이 틀리는" 종류다

1. **비율지표를 통화 무시하고 합산하던 문제** — 집약도의 분모(매출액)는 법인별 현지통화다.
   KRW·CNY·VND를 그대로 더하면 숫자는 나오지만 아무 의미가 없다.
   이제 연평균환율로 원화 환산 후 합산하고, **환율이 없으면 합산하지 않고 "환율 미등록"으로
   미산정 처리**한다 (R65).
2. **재산정할 때마다 결과가 쌓이던 문제** — `calc_result` 의 UNIQUE 제약에 `site_id` 가 들어
   있고 법인 합산 행은 그 값이 NULL 이다. SQLite 는 UNIQUE 안의 NULL 을 서로 다른 값으로
   보므로 `ON CONFLICT` 가 걸리지 않았다. 연간 합계가 재산정 횟수만큼 커졌을 것이다.
3. **합계가 법인별 값의 합과 어긋나던 문제** — 반올림 전 값으로 합산하면 보고서에 인쇄된
   3법인 수치를 더했을 때 합계와 0.01 차이가 난다. 그 질문에는 답할 방법이 없다.
   월 → 연 → 그룹 모두 **반올림한 값으로 누적**한다.
4. **집약도가 0.0000 으로 표시되던 문제** — 값이 없는 것과 0 인 것이 화면에서 구별되지
   않았다. 배수를 두어 `GJ/억원` · `tCO2eq/억원` 으로 읽을 수 있게 했다.

R64 검증 — 이 설계가 필요한 이유 (`npm run g3` [4]절 출력)

| 지표 | 3법인 합산 | 법인별 값의 평균 | 차이 |
|---|---|---|---|
| 에너지 집약도 | 21.54 | 34.42 | **59.8%** |
| 배출 집약도 | 3.37 | 5.34 | **58.7%** |
| 재해 도수율 | 7.06 | 5.92 | **16.2%** |
| 이직률 | 5.15 | 4.52 | **12.4%** |

법인별 비율을 평균하면 그룹 값이 되지 않는다. 그래서 분자·분모를 각각 저장하고
집계 시점에 다시 나눈다.

## 승인 흐름

```
미입력 ──▶ 입력완료 ──▶ 승인 ──▶ 확정
              ↘ 반송 ──▶ 입력완료
미입력 ──▶ 미확보 ──(승인)──(확정)──▶ 끝까지 "미확보" 로 남는다
```

| 단계 | 권한 | 하는 일 |
|---|---|---|
| 1단 승인 | 본사 ESG 총괄 (manager) | 항목별 승인 · 반송(사유 4종 선택형) |
| 2단 확정 | 파트장 (approver) · 시스템 관리 | 기간 전체 확정. **확정 시 배출량이 산정·저장된다** |

**미확보 항목은 승인·확정해도 상태가 "미확보" 로 남는다.** 승인 시각만 기록한다.
"승인된 미확보"가 "승인된 값"과 같은 상태가 되면, 보고서를 쓸 때 그 칸이 빈 이유를
설명할 수 없게 된다 (D-2).

확정은 **빈칸이 하나라도 있으면 막힌다.** 무엇이 막고 있는지와 해야 할 일을
화면이 항목별 건수로 알려준다. 확정을 풀면(`재개방`) 원본은 지우지 않고 상태만
되돌리며, 모든 상태 변경은 `audit_log` 에 남는다 (R58).

## 개발 원칙

자체 수행을 성립시키는 여섯 가지. 하나라도 깨지면 중간에 멈춘다.
상세는 `docs/planning/ep08-roadmap.md` 2절.

1. **파일을 작게, 적게 유지한다** — AI가 관련 코드를 한 번에 볼 수 있어야 수정이 정확하다.
   W3 기준 앱 코드 8개 파일(`src/` 4 · `public/` 4), 각 800줄 안팎.
   기능이 늘어도 파일을 쪼개는 대신 한 화면을 한 파일에 담는다
2. **빌드 단계를 만들지 않는다** — 빌드가 실패하면 비개발자는 원인을 추적할 수 없다
3. **하루 1기능, 끝나면 즉시 배포·확인** — 한 번에 다 만들면 어디서 틀렸는지 알 수 없다
4. **스키마를 먼저 확정하고 바꾸지 않는다** — 흔들리면 만든 화면을 전부 다시 만들어야 한다
5. **가짜 데이터부터 넣고 눈으로 확인한다**
6. **오류는 메시지 전문을 AI에게 붙여넣는다** — 요약하면 AI도 추측만 한다
