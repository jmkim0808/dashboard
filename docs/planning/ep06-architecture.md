# EP6. 무엇으로 만드나 — 아키텍처 · 비용 · 보안 · 유지보수

> 목적: 자체 웹앱(Cloudflare + Claude API)의 구성을 확정하고, **비용·보안·유지보수 난이도**를 정직하게 산정한다.
>
> 전제: 사내 전산팀 없음. 유지보수 주체는 **경영지원실 파트장 + AI 도구**.
> 이 전제가 기술 선택의 최상위 제약이다. "최신 스택"이 아니라 **"1년 후에도 내가 고칠 수 있는 스택"** 을 고른다.

## 1. 🔴 중국 본토 접속 — 아키텍처 확정 전 필수 검증

### 확인된 사실

| 항목 | 상태 |
|---|---|
| **Cloudflare Pages (`*.pages.dev`)** | **중국 본토에서 제공되지 않음.** `pages.dev` 인증서가 중국 본토에 없음 |
| **Cloudflare Workers (`*.workers.dev`)** | 중국에서 접속 불안정·타임아웃 사례 다수 보고 |
| Cloudflare 전반 | GFW의 DNS 오염·SNI RST 방식으로 **도메인별로 차단 여부가 다르고 시점에 따라 변동** |
| Cloudflare China Network | 존재하나 **Enterprise 플랜 + 중국 파트너(JD Cloud) + ICP 등록** 필요 → 본 프로젝트 범위 초과 |

### 이것이 의미하는 바

> **심양 법인 담당자(P7)가 접속하지 못하면 이 프로젝트는 3법인 통합이 아니다.**
> 그리고 3법인 통합이 아니면 EP2의 전제(그룹 합산 데이터)가 무너진다.

### 대안 비교

| 대안 | 내용 | 판단 |
|---|---|---|
| **A (권고)** | **자체 커스텀 도메인 사용** — `esg.powernet.co.kr` 형태. `pages.dev` / `workers.dev` 를 직접 노출하지 않는다. 인증서 문제는 해소되나 **GFW 차단 여부는 보장되지 않는다** | ✅ 기본안. **단 반드시 사전 검증** |
| **B (폴백)** | 심양만 **별도 경로** — 엑셀 템플릿 이메일 제출 → 본사에서 업로드(S3 파일 업로드 화면 재사용) | ⚠️ EP1로의 부분 회귀. 단 **차선책으로 확보 필수** |
| C | 중국 내 접근 가능한 대체 채널 (위챗 미니프로그램, 알리클라우드) | ❌ 비용·복잡도 급증. 전산팀 없는 조건에서 불가 |
| D | Cloudflare China Network 도입 | ❌ Enterprise 플랜 + ICP 등록(중국 법인 명의). 범위 초과 |

### 🔴 즉시 검증 방법 (EP8 첫 2주 과제)

1. 자체 도메인 서브도메인 하나에 **Cloudflare Pages 테스트 페이지 배포** (1시간 작업)
2. 심양 담당자에게 **① 회사 유선망 ② 모바일 데이터** 두 경로로 접속 테스트 요청
3. 로딩 시간과 성공률 기록 (최소 3일, 하루 2회)
4. 실패 시 **대안 B로 설계 확정** — 이 경우 심양용 화면(S1) 개발이 불필요해지므로 **개발 범위가 오히려 줄어든다**

> **이 검증이 끝나기 전에 개발을 시작하지 않는다.** 검증 결과가 아키텍처를 바꾼다.

## 2. 아키텍처

### 2-1. 구성도

```
┌─────────────────────────────────────────────────────────────┐
│  사용자 10명 (본사 6 · 심양 1 · 빈푹 1 · 파트장 · 대표이사)      │
│  PC 브라우저 / 모바일 브라우저                                  │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTPS  esg.powernet.co.kr
                 ┌──────────▼───────────┐
                 │ Cloudflare Access    │ ← 인증 (50명 무료)
                 │ 이메일 OTP / SSO      │   자체 로그인 구현 없음
                 └──────────┬───────────┘
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
┌───────▼────────┐  ┌───────▼────────┐  ┌──────▼──────────┐
│ Cloudflare     │  │ Cloudflare     │  │ Cloudflare      │
│ Pages          │  │ Workers        │  │ R2              │
│ (화면·정적파일) │  │ (API·산정로직)  │  │ (증빙 파일)      │
└────────────────┘  └───┬────────┬───┘  └─────────────────┘
                        │        │
              ┌─────────▼──┐  ┌──▼──────────────┐
              │ D1 (SQLite)│  │ Claude API      │
              │ 입력·마스터 │  │ 증빙 숫자 추출   │
              └────────────┘  └─────────────────┘
                        │
              ┌─────────▼──────────┐
              │ 이메일 알림 (Resend)│ ← 마감 리마인드
              └────────────────────┘
```

### 2-2. 계층별 선택과 이유

| 계층 | 선택 | 이유 |
|---|---|---|
| **인증** | **Cloudflare Access (Zero Trust)** | 50명 무료. **자체 로그인·비밀번호·세션 관리를 구현하지 않는다** → 가장 흔한 보안 사고 유형을 구조적으로 제거. 이메일 OTP면 계정 발급도 단순 |
| **화면** | Cloudflare Pages | 정적 호스팅 무료, 대역폭 무과금 |
| **API·로직** | Cloudflare Workers | 서버 관리 불필요. 산정 로직을 코드로 고정(R4) |
| **DB** | Cloudflare D1 (SQLite) | Workers Paid에 포함. 데이터량이 극소하므로 충분 (아래 산정 참조) |
| **파일** | Cloudflare R2 | 10GB 무료. 증빙 파일 보관 |
| **AI** | Claude API (Workers에서 호출) | 증빙에서 숫자 추출 (4절) |
| **알림** | 이메일 발송 서비스 | 마감 리마인드 자동화 (R16, P-4) |

### 2-3. 데이터량 산정 — D1으로 충분한가

| 항목 | 산정 |
|---|---|
| 월 입력 행 수 | 약 70행 (본사 20 + 심양 24 + 빈푹 24) |
| 연 입력 행 수 | 약 840행 |
| 소급분 (2025~2026, 24개월) | 약 1,680행 |
| **5년 누적** | **약 6,000행** |
| 산정결과·이력·마스터 포함 | 약 30,000행 |

> D1의 Workers Paid 포함 한도는 **읽기 250억 행/월, 쓰기 5천만 행/월, 저장 5GB**다.
> 우리 규모는 한도의 **0.001% 미만**이다. **D1 용량은 고려 대상이 아니다.**

### 2-4. 🔴 프레임워크 선택 원칙 — 이 프로젝트의 핵심 기술 판단

> **유지보수 주체가 파트장 + AI라면, 빌드 체인이 복잡한 순간 6개월 후 수정 불가 상태가 된다.**

| 구분 | 권고 | 배제 |
|---|---|---|
| 프론트엔드 | **소수 의존성 + 서버 렌더링 중심.** 화면 수가 11개고 사용자가 10명이다. 복잡한 상태관리가 필요한 화면이 없다 | 무거운 SPA 프레임워크 + 빌드 파이프라인. 의존성 업데이트가 연 단위 부채가 된다 |
| 빌드 | **빌드 단계 최소화.** 코드를 고치면 바로 반영되는 구조 | 트랜스파일·번들러 다단 구성 |
| 스타일 | 단일 CSS 파일 또는 유틸리티 CSS 1종 | 디자인 시스템 다중 도입 |
| 라이브러리 | **꼭 필요한 것만** (차트 1종, 날짜 처리 1종 수준) | "있으면 편한" 라이브러리 누적 |

- **R74** 의존성 수를 최소화한다. **의존성 1개를 추가할 때마다 "1년 후 이것을 내가 업데이트할 수 있는가"를 판정**한다.

> 이것은 기술적 취향이 아니라 **리스크 관리**다. 화려한 스택으로 만든 플랫폼이
> 유지보수 불가로 방치되는 것이, 단순한 스택으로 5년 굴러가는 것보다 나쁘다.

### 3-2. Claude API — 증빙 숫자 추출

증빙 이미지(고지서·전표 사진)에서 숫자를 읽어 **입력값을 제안**하는 용도다.

| 항목 | 산정 |

## 4. Claude API 활용 — 증빙 자동 추출

### 4-1. 유스케이스와 우선순위

| 우선순위 | 용도 | 효과 |
|---|---|---|
| **1** | **증빙 이미지 → 숫자·단위 추출 제안** | 담당자는 사진만 찍는다. 입력 시간 단축 + **자릿수·단위 오류 감소** (EP1 만kWh 사건) |
| 2 | 이상치 발생 시 **확인 질문 생성** (현지어) | "전월 대비 +920%입니다. 단위가 万kWh인지 확인해 주세요" |
| 3 | 항목명·안내문 **다국어 번역 초안** | 현지 담당자 검수 전 초안. 최종 확정은 사람이 (R27) |
| 4 | 보고서 집필 시 **지표 데이터북 기반 초안 작성** | 2027년 보고서 제작 단계 |

### 4-2. 🔴 절대 규칙 — 추출값은 "제안"이다

> **Claude가 추출한 숫자를 자동 저장하지 않는다.**

이유는 설계원칙 P-2와 동일하다. 자동 저장은 **출처를 알 수 없는 숫자**를 만든다.
EP1의 "추정치 12칸"과 구조적으로 같은 문제다.

동작 흐름:

```
담당자가 고지서 사진 첨부
        ↓
Claude가 숫자·단위 추출 → 입력칸에 "제안값"으로 회색 표시
        ↓
담당자가 확인 후 확정 (또는 수정)
        ↓
확정값과 함께 "AI 제안값"도 별도 저장
        ↓
제안값 ≠ 확정값인 건은 검증 화면에서 표시
```

- **R72** Claude 추출값은 **제안**이며 자동 확정되지 않는다. **추출값과 확정값을 분리 저장**하고, 불일치 건은 검증 화면에서 확인 가능하다.

> 부수 효과: 제안값과 확정값의 불일치율을 보면 **추출 정확도를 측정**할 수 있다.
> 정확도가 충분히 높아지면 나중에 자동 확정 범위를 넓힐지 판단할 근거가 된다.

| 한국 | 개인정보보호법 | — | 국외이전 시 동의·고지 요건 |

> 🔴 **즉 3개국 모두 2026년부터 개인정보 국외이전 제재가 강화됐다.**
> 인사·안전보건 데이터를 다루는 이 플랫폼은 이 문제를 피할 수 없다 — **설계로 피해야 한다.**

### 5-2. 🔴 해법 — 설계원칙 P-8 신설

> ### **P-8. 개인 단위 데이터는 플랫폼에 올리지 않는다. 집계값만 올린다.**

**개인을 식별할 수 없는 통계·집계값은 개인정보가 아니다.** 따라서 국외이전 규제의 대상이 아니다.

| ❌ 올리지 않는다 | ✅ 올린다 |
|---|---|
| 직원 명단, 사번, 이름 | "2027년 4월 심양법인 총 인원 182명" |
| 개인별 근로시간·급여 | "총 근로시간 31,240시간" |
| 재해자 이름·상병명 | "재해 1건, 근로손실일수 12일" |
| 개인별 교육 이수 내역 | "총 교육시간 420시간" |
| 주민번호·여권번호·연락처 | (해당 없음) |

EP5의 S 지표 체계는 **이미 전부 집계값**이다(S01~S14). 따라서 **지표 설계를 바꿀 필요가 없다.**
필요한 것은 **이 원칙을 명문화하고, 증빙 첨부에서 새는 것을 막는 것**이다.

- **R70** 개인을 식별할 수 있는 데이터는 어떤 항목에도 입력되지 않는다. 입력 화면에 이를 명시한다.

### 5-3. 🔴 증빙 첨부의 구멍 — E 지표와 S 지표를 다르게 다룬다

R28은 "증빙 첨부 필수"였다. 그런데 **S 지표의 증빙은 개인정보를 포함한다.**

| 지표군 | 증빙 원천 | 개인정보 포함 | 증빙 정책 |
|---|---|---|---|
| **E (환경)** | 전기·수도·가스 고지서, 폐기물 위탁 전표 | 없음 | **증빙 필수** (R28 유지) |
| **S (사회)** | 급여대장, 근태표, 재해조사표, 교육 이수 명부 | 🔴 **포함** | **원본 증빙 첨부 금지.** 집계표(이름·사번이 제거된 부서·법인 단위 합계)만 허용 |
| 생산 | ERP 추출 자료 | 없음 | 증빙 필수 |

- **R71** S 지표는 **개인정보가 제거된 집계 증빙만 허용**한다. 급여대장·근태표·재해조사표 원본 업로드는 시스템이 거부한다(안내 포함). **R28의 명시적 예외**다.

> 이 한 줄이 없으면, 선의의 담당자가 급여대장 PDF를 첨부하는 순간
> 중국·베트남 개인정보 국외이전 위반이 성립할 수 있다. **화면에서 막아야 한다.**

### 5-4. 그 외 보안 사항

| 항목 | 조치 |
|---|---|
| 인증 | **Cloudflare Access.** 자체 로그인·비밀번호 저장·세션 관리를 구현하지 않는다 → 가장 흔한 취약점 유형 제거 |
| 접근 격리 | 법인 단위 데이터 격리 (R62). 심양 담당자는 빈푹 데이터 조회 불가 |
| 전송 | HTTPS 전구간. Cloudflare 기본 제공 |
| 증빙 파일 | R2 비공개 버킷. 서명 URL로만 접근. 직접 URL 노출 금지 |
| 감사 로그 | 모든 변경 이력 보존 (D-4, R45) |
| 백업 | **D1 자동 백업에만 의존하지 않는다.** 월 1회 전체 데이터 엑셀 덤프를 별도 보관 (아래 R76) |
| 데이터 저장 위치 | ⚠️ **확인 필요** — R2 location hint, D1 리전 설정 가능 범위. 집계값만 다루므로 규제 리스크는 낮으나 확인은 필요 |

- **R76** **월 1회 전체 데이터 엑셀 덤프**를 자동 생성해 별도 저장소에 보관한다. 플랫폼이 사라져도 데이터는 남는다.

> R76은 유지보수 1인 의존 리스크의 최소 보험이다. 파트장이 부재하고 플랫폼이 멈춰도,
> 엑셀 덤프가 있으면 EP1 상태로 되돌아가는 것이 아니라 **데이터는 보존된다.**

## 6. 유지보수 — 정직한 평가

### 6-1. 이 구조의 최대 약점

> **월 $6의 대가는 "유지보수 1인 의존"이다.**

| 발생 가능 상황 | 결과 |
|---|---|
| 파트장 부재(휴가·병가·전배·퇴사) | 장애 발생 시 복구 주체 없음 |
| Cloudflare 정책·API 변경 | 대응 주체 없음 |
| 배출계수·환율 갱신 | **화면에서 가능하게 설계하면 코드 수정 불필요** (아래) |
| 항목 추가·지표 변경 | **동일 — 화면에서 가능하게** |
| 신규 법인 추가 | 코드 수정 필요 |

### 6-2. 🔴 완화 전략 — 핵심은 "코드를 건드릴 일을 없애는 것"

| # | 전략 | 내용 |
|---|---|---|
| **1** | **마스터 변경은 전부 화면에서** | 배출계수 추가, 환율 갱신, 항목 추가·폐지, 담당자·부담당자 변경, 단위 변경, 공개등급 변경, 프레임워크 매핑 — **전부 관리 화면에서.** 코드 수정이 필요한 변경을 남기지 않는다 |
| **2** | **의존성 최소화** | R74. 1년 후 업데이트 가능한 것만 |
| 3 | **운영 문서화** | 배포 방법, 계정 발급, 장애 시 확인 순서를 **화면 안에 또는 저장소에** 문서로. 구두 인수인계 금지 |
| 4 | **외부 개발자 유지보수 계약 검토** | 연 단위 소액 계약(월 수십만원 수준)으로 장애 대응 창구 확보. **구축이 아니라 유지보수만** |
| 5 | **월간 엑셀 덤프** | R76. 최악의 경우에도 데이터는 남는다 |

- **R73** 마스터성 변경(계수·환율·항목·담당자·단위·공개등급·매핑)은 **전부 관리 화면에서 수행 가능**해야 한다. 코드 수정을 요구하는 운영 변경을 남기지 않는다.

> **R73이 이 프로젝트에서 가장 중요한 유지보수 요구사항이다.**
> 이것이 지켜지면 연간 코드를 건드릴 일이 거의 없고, 지켜지지 않으면
> 배출계수가 개정되는 매년 파트장이 코드를 고쳐야 한다.

### 6-3. 난이도 등급

| 작업 | 난이도 | 주체 |
|---|---|---|
| 매월 운영 (입력 독려·검증·승인) | 낮음 | P1 |
| 계수·환율·항목·담당자 변경 | **낮음 (화면)** | P1 / 파트장 |
| 화면 문구·안내 수정 | 중간 | 파트장 + AI |
| 신규 지표·화면 추가 | 중간~높음 | 파트장 + AI |
| 장애 대응 (배포 실패·DB 오류) | **높음** | 🔴 파트장 단독 → 외부 계약 검토 |
| 신규 법인 추가 | 높음 | 파트장 + AI |
